```bash
  --normalize \

  --skip-existing \
  --sleep-ms 25
```

### 2.2 オプション指針

* `--batch 256`: i3-6100T / RAM 8GB 想定の安全幅。重ければ 128 に落とす。
* `--skip-existing`: 既に `emb` が入っている chunk は飛ばす（再実行安全）。
* `--normalize`: コサイン前提の正規化をオン（`<=>` cos 距離と整合）。
* `--sleep-ms`: I/O 休止で負荷分散。Prometheus scrape やAPIのレスポンス悪化を避ける。
* `--max-retries`: ネットワーク／一時的な失敗を再試行。

> `scripts/embed_chunks.py` が未対応なら、下の **2.3 パッチ** を適用（CodexCLIに貼るだけでOK）。

## 3) HNSWインデックス作成/確認（cos演算）

**既存インデックスがない場合のみ**作成。名前は一意に（重複禁止）。

```sql
-- 既存を確認（1)で未検出なら作成）
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_chunk_emb_hnsw_cos
ON chunk
USING hnsw (emb vector_cos_ops)
WITH (m = 16, ef_construction = 64);

-- インデックス統計
SELECT relname, pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_index i JOIN pg_class c ON c.oid=i.indexrelid
WHERE indrelid='chunk'::regclass AND c.relname='idx_chunk_emb_hnsw_cos';

-- 併せてANALYZE
ANALYZE chunk;
```

> 既に `idx_chunk_vec_hnsw_bge_m3_cos` のような命名がある場合は**作成不要**。以降の検証で使われているかを見ます。

## 8) トラブルシュート（現場最短版）

* **MemoryError/落ちる** → `--batch 128` または `--sleep-ms 50`。
* **インデックス作成が重い** → `CREATE INDEX CONCURRENTLY`（既に指定）、夜間実行。
* **EXPLAINがSeqScan** → `ANALYZE chunk;`、`enable_seqscan=off` で試験、`amname='hnsw'` の指数が本当にあるか確認。
* **emb 次元エラー** → `vector(768)` で再作成が必要。既存列の型を `ALTER TABLE ... ALTER COLUMN emb TYPE vector(768);`（要ダウンタイム）。
* **部分的に未埋め** → 同コマンドで再実行（`--skip-existing` があるので差分のみ埋める）。
